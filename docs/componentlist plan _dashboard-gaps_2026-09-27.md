## 2. Non-negotiable rules (same as batch 2)

- No raw values. Atlas tokens only (`--atlas-*`, semantic tokens, no primitive refs in app code).
- A missing token goes to Figma foundations first, then code tokens, then the component.
- No code until the Figma page has an explicit **"approved"** reply from the user in chat.
- No next phase until the previous one has final approval.
- Figma wins over code and drives it. If code needs something Figma does not draw, fix Figma first.
- Figma work goes through the authenticated Figma MCP only.
- No new dependencies unless the audit shows the existing foundation (Radix installs already in the repo: `@radix-ui/react-checkbox`, `-dialog`, `-tabs`) can't cover it — flag at audit, don't assume.
- Per AGENTS.md §4: **no new component is added on the agent's own initiative.** Every Track B item is a `candidates.json` entry today; it becomes a component only after a Figma design exists and the user approves promoting it. This plan proposes the list and order — it is not itself the approval.
- `atlas/` is generated, never hand-edited.

## 3. Workflow per phase (A to E) — unchanged from batch 2

- **A. Audit.** Read the relevant Figma node (or, for Track B, confirm no node exists yet and the component must be designed from scratch) against Atlas foundations and existing components. Post a mapping table, proposed tokens/props and gaps. Wait for the user's answers. One audit per phase, at the start of that phase.
  **When the audit leans on an external reference** (a ReUI/shadcn node, or any pattern outside Atlas's own file) **or asks the user to accept a new anatomy**: fetch that reference and screenshot it — don't propose structure from a metadata dump or from memory. The audit deliverable is the reference screenshot plus a written anatomy/token mapping (what node maps to what Atlas token), and it needs an explicit "approved" on that mapping before any `use_figma` write call, not just approval of the general direction. (Added 2026-09-27 after a Dialog/Sheet/Drawer audit skipped this and drew from a metadata summary instead of the actual reference, twice.)
- **B. Figma.** Load `figma:figma-use` and `figma:figma-generate-library` before `use_figma`. For Track A, edit the existing component page to close the discrepancy. For Track B, create a new page after the last component page; build the component set with properties, Light/Dark examples, and a usage panel, following the existing page layout. Bind everything to variables.
- **C. Gate 1.** User replies "approved".
- **D. Code.** `atlas-figma-sync` pull; implement via `atlas-component`; Code Connect file in `packages/figma-sync/code-connect/`; contract in `packages/governance/contracts/`; vitest + jest-axe tests; sandbox section in `app/page.tsx`; `atlas-verify` (`node scripts/atlas-verify.mjs --allow-new-component --scope "<globs>"` for Track B, no flag needed for Track A prop-only fixes).
- **E. Gate 2.** User replies "approved", then commit on the phase's branch and merge `--no-ff` to `main`. Trailer: `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`. Push only when asked.

Audit found: (a) Figma's `Variant` (default/destructive) has zero chrome effect — only the example's own confirm-button color differs, so it's a semantic marker, not a structural variant; (b) Figma has **no sheet or drawer content at all** — "add Type" meant authoring two full new presentations from scratch, not a rename.
